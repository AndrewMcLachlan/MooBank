# Theme 2 — Tenant Isolation Ownership

## Context

The review found tenant isolation enforced at three layers with no defined owner, one real gap (`GetTagTrendReport` cross-family tag read), dead duplicate checks (Tags), inconsistent cross-family idioms (404 vs 403+audit), and uneven denial auditing.

**User decisions:**
- Governing principle: **auth should be handled by policies and requirements wherever possible** (goal state). Filtering — global query filters or per-query — is welcome **defence-in-depth**, not the primary control.
- Adopt EF global query filters; the deleted-tags concern is answered by EF 10 **named query filters** (soft-delete and tenancy registered separately; `IgnoreQueryFilters(["SoftDelete"])` shows deleted rows without ever lifting the family filter).
- Unify denial auditing in the handler bases.

## The contract (to be documented in `.claude/rules/backend/rest-api.md`)

1. **Single-resource routes** (id in route) → parameterized policy backed by a route-based requirement handler (403 + audit on denial). Non-route contexts (MCP tools, command-body foreign keys) → resource-based requirement, invoked via `ISecurity`.
2. **Collection/list endpoints** → handler/query filtering by user/family (policies cannot scope lists); global query filters make this structural.
3. **Repository and global query filters are defence-in-depth** for id routes and the primary mechanism for lists. Redundancy with a policy is acceptable; a policy-less id route is not (where a suitable requirement exists).

## Changes

1. **Fix `GetTagTrendReport`** (`src/MooBank.Modules.Reports/Queries/GetTagTrendReport.cs:22`): add `t.FamilyId == user.FamilyId` to the tag lookup. Ship regardless of the policy work below (defence-in-depth).
2. **Tag route policy** (the goal-state fix, mirrors the BudgetLine pattern from PR #862):
   - Add `Task<Guid?> GetTagFamilyId(int tagId, CancellationToken)` to `IAuthorisationRepository` (`src/MooBank.Domain/IAuthorisationRepository.cs`) + implementation in `SecurityRepository` (decision-free data query).
   - New `TagFamilyRequirement` + route-based handler (route `{id}`/`{tagId}` → `GetTagFamilyId` → compare `user.FamilyId`; audit on denial) + resource-based pair for non-route use. Follow `BudgetLineAuthorisationHandler` (`src/MooBank.Security/Authorisation/BudgetLineAuthorisationHandler.cs`) including the `RequestAborted` cancellation propagation.
   - Register policy factory (e.g. `Policies.GetTagFamilyPolicy(paramName)`); apply to `/tags/{id}` endpoints (Get/Update/Delete/AddSubTag/RemoveSubTag in `src/MooBank.Modules.Tags/Endpoints/Tags.cs`) and to the tag-trend report route (`{tagId}` param) so the leak is closed at the policy layer too.
   - Remove the now-dead `security.AssertFamilyPermission(...)` calls from Tags command handlers (Update/Delete/AddSubTag/RemoveSubTag). Keep `TagRepository`'s family filter as defence-in-depth (or drop once global filters land — see 3).
3. **EF 10 named global query filters on Tag** (pilot; evaluate wider rollout after):

# Theme 3 — Names That Lost Their Meaning

## Context

`[AggregateRoot]` is used as a DI switch, "Repository" covers read-model gateways, child entities have their own repositories, and `RepositoryDeleteBase.Delete(id)` is a runtime `NotImplementedException` trap.

**User decisions:**
- Rename read-model gateways (Reader/ReadRepository naming).
- Route child-entity access through the real aggregate root.
- `[AggregateRoot]`: no new ASM mechanism — strip from non-roots and rewrite consumers to **start at the real aggregate root and work down** via navigations.
- Delete verb: polymorphic by design — soft-vs-hard is the implementer's decision, callers are agnostic. **Fix the trap only**; keep the `Delete` name everywhere.

## Changes

1. **Rename read-model gateways**:
   - `IReportRepository` → `IReportReader` (impl `ReportRepository` → `ReportReader`); stays in `MooBank.Domain/Entities/Reports/` (naming open to adjustment at review — the point is it stops claiming aggregate semantics). Update the 14 Reports query handlers and DI registration.
   - `SecurityRepository` class → `AuthorisationRepository` (matches its `IAuthorisationRepository` interface; it is a decision-free data-query service).
   - `ReferenceDataRepository`: keep the name (it has a genuine write side used by background jobs) but normalise the mixed sync/async `Add` semantics; note a per-entity-type split as optional follow-up, not in scope.
   - Rules docs: define the two concepts — *Repository* = aggregate-root write side; *Reader* = read-model gateway (SPs, reference data), used by query handlers where `IQueryable<T>` doesn't fit.
2. **Route child entities through the Instrument aggregate**:
   - Remove `IRuleRepository`/`RuleRepository`: rules CRUD (Instruments module `/instruments/{id}/rules` endpoints) goes through `IInstrumentRepository` + a rules specification, with mutation behaviour on the `Instrument` entity (e.g. `AddRule`/`RemoveRule`/`UpdateRule` — the entity gains real behaviour, aligning with Theme 4's richness push). This also removes `RuleRepository.GetById`'s unfiltered-by-tenant path.
   - Remove `IRecurringTransactionRepository`: the recurring-transactions job (`src/MooBank/Services/RecurringTransactions.cs`) and any handlers load via `IInstrumentRepository` + the existing `RecurringTransactionSpecification` (already loads through the root — currently the *second* competing path; it becomes the only one). Mutations via `VirtualInstrument` methods.
   - Design specifications deliberately (house rule: no defensive Includes); verify query shape/perf on the job path.
3. **`[AggregateRoot]` back to a boundary marker**:
   - Strip from `BudgetLine` (`src/MooBank.Domain/Entities/Budget/BudgetLine.cs:5`) and `TagRelationship`; keep on `ImporterType` (standalone reference-data root, no parent).
   - Rewrite consumers to start at the real root: `IQueryable<BudgetLine>` sites → `IQueryable<Budget>` + `SelectMany(b => b.Lines)`/root-first predicates (bonus: tenancy comes free — `FamilyId` lives on the root); `IQueryable<TagRelationship>` sites (`Modules.Tags/Commands/AddSubTag.cs` circular check, `Modules.Budgets/Commands/Generate.cs`) → navigate from `IQueryable<Tag>`. During implementation, verify each query is expressible from the root with equivalent SQL; if one genuinely is not, surface it before working around.
   - Rules doc gets the principle (agreed in discussion): *query children through their root; if that is persistently impractical for an entity, that is evidence it is actually an aggregate root — promote it deliberately rather than injecting child IQueryables.*
   - Note: `BudgetLineAuthorisationHandler`'s data path already goes through `IAuthorisationRepository`, not `IQueryable<BudgetLine>` — unaffected.
4. **Fix the `RepositoryDeleteBase` trap**: make `Delete(TKey)` abstract in `src/MooBank.Infrastructure/Repositories/RepositoryDeleteBase.cs` (compile-time obligation instead of runtime throw), implementing it on the types that currently inherit the trap (`TagRepository`, `LogicalAccountRepository`; `RuleRepository` disappears in change 2). Document the polymorphic-Delete principle in `.claude/rules/backend/entity-framework.md`: *Delete semantics (soft/close/flag/hard) are the repository implementation's decision; callers never assume which.*

## Verification

- Full build + full test suite; grep for `IReportRepository|RuleRepository|IRecurringTransactionRepository` → 0 hits.
- Rules/recurring-transaction flows: unit tests retargeted to aggregate methods; manual check of rules CRUD in the UI and the recurring-transaction job run (AppHost).
- SQL sanity on rewritten root-first queries (log/inspect generated SQL for the AddSubTag circular check and budget-line queries — no N+1 or cartesian blowups).

# Theme 4 — One Pattern, One Implementation

## Context

Several deliberate idioms have accidental twins: two specification-application extensions, three event-raising sites, three command-binding styles, arbitrary audit coverage, and (frontend) three mutation-invalidation idioms plus scattered formatting.

**User decisions:** ASM `.Specify()` everywhere; **all user mutations audited**; domain events **move into aggregates**; Budgets `Generate` **refactored to the rule**.

## Backend changes

1. **`.Specify()` everywhere**: delete `src/MooBank.Domain/SpecificationExtensions.cs` (local `.Apply()`); convert the ~13 call sites to ASM's `.Specify()`. Update the rules-doc examples (`backend/cqrs.md`, `backend/entity-framework.md`) to `.Specify()` — this supersedes Theme 1's as-is treatment of those code samples (coordinate if Theme 1 ships first).
2. **Audit rule — all user mutations**: every user-initiated command handler saves via `IAuditingUnitOfWork` (~53 handlers switch from `IUnitOfWork`); plain `IUnitOfWork` is reserved for system/background flows (jobs, importer internals, domain-event-driven saves). Mechanical swap; document the rule in `backend/cqrs.md`. (Per the audit-log definition: user actions including data changes are audit events; system outcomes are not.)
3. **Events raised in aggregates only**:
   - `VirtualInstrument.AdjustBalance(decimal)` raises `BalanceAdjustmentEvent`; `Modules.Instruments/Commands/VirtualInstruments/Update.cs` and `UpdateBalance.cs` call it instead of appending to `.Events`.
   - Instrument lifecycle events (`InstrumentCreatedEvent`/`InstrumentUpdatedEvent`/`AccountAddedEvent`) move out of the five repository `Add`/`Update` overrides (`InstrumentRepository`, `LogicalAccountRepository`, `AssetRepository`, `StockHoldingRepository`, `UtilityAccountRepository`) into entity factories/methods on the respective aggregates (follow the `Transaction.Create` pattern).
   - Unify the duplicate balance-change mechanism: `Modules.Transactions/Commands/UpdateBalance.cs` (directly creates a transaction) adopts the same domain-method+event path, so "balance change ⇒ adjustment transaction" has one implementation.
   - Repositories and handlers no longer touch `.Events` anywhere (grep-verifiable).
4. **Budgets `Generate` refactor** (`src/MooBank.Modules.Budgets/Commands/Generate.cs`): mutations go through `IBudgetRepository` (+ a budget-with-lines specification replacing the inline Includes); the transaction-history analysis inputs come from a read gateway (Theme 3 Reader concept — e.g. a small analysis reader, or existing readers) rather than five injected `IQueryable<T>`s. `RunForecast` keeps its `IQueryable` (it writes nothing) and is documented in `backend/cqrs.md` as a computation POST — an acknowledged query-shaped command.
5. **Command binding**: replace the two hand-rolled `BindAsync` implementations (`Modules.Instruments/Commands/VirtualInstruments/Update.cs:18-27`, `UpdateBalance.cs:17-26` — manual `JsonSerializer` + route parsing) with attribute-annotated records like `Modules.Families/Commands/Update.cs`. (The other live `BindAsync` implementations under `CommandBinding.None` stay — they exist for binding shapes the attribute style can't express.)
6. **Specification naming**: document the convention for new specifications (`XxxDetailsSpecification` for include bundles, verb-named for filtered loads) in `backend/csharp.md`; no renames of existing ones (churn without behaviour value). The two identical `IncludeSpecification`s stay (per-aggregate types; merging needs a shared base that isn't worth it).

# Theme 5 — Layering and the Core

## Context

Domain references the DTO assembly (for shared enums), causing the two-assembly `Asm.MooBank.Models` namespace split; the core `src/MooBank` project mixes abstractions with hosted services; core references concrete integration clients; jobs are hosted in the API.

**User decisions (with DDD rationale discussed):**
- Shared enums → **new shared-kernel project**. Principle refined: "nothing in Domain exposed via API" applies to domain *objects/behaviour*; enums are ubiquitous-language vocabulary shared via a Shared Kernel, so the principle holds to the letter and no duplication/mapping is needed.
- Core `src/MooBank` project: **leave as-is**; document its role.
- Integration clients: **invert** — interfaces in core, concrete wiring in the composition root.
- Jobs stay hosted in the API — **document** (covered by Theme 1).

## Changes
